# MCP specification 2026-07-28 adoption status

The gateway speaks MCP protocol 2025-11-25 (SDK `^1.29.0`). The 2026-07-28
revision is tracked actively; everything below is either already live at the
gateway layer or explicitly waiting on SDK support. The gateway never
advertises `2026-07-28` as a supported protocol version anywhere - every
claim below is about behavior implemented ahead of that SDK bump, not about
a version number this deployment does not actually speak.

## Live now (this release)

| Spec item | Gateway behavior |
|---|---|
| Mcp-Method / Mcp-Name headers (SEP-2243) | Validated against the JSON-RPC body when present (`Mcp-Method` against `method`, `Mcp-Name` against `params.name`/`params.uri`); mismatch, or a header that fails to decode, returns HTTP 400 with JSON-RPC error `-32020`. Neither header present leaves behavior unchanged - this is validate-if-present, not require. |
| server/discover (SEP-2575) | A well-formed `server/discover` request is answered directly at the route layer, before the SDK transport ever sees it, with `resultType: "complete"` and the honest legacy `supportedVersions` set so a modern client can negotiate down cleanly instead of hitting the SDK's `-32601 Method not found`. A discover *notification* (no `id`) falls through unchanged. |
| requestState integrity (SEP-2322) | Pending HITL envelopes on both transports carry an HMAC-bound `requestState` (principal, expiry, digest of the originating tool call). `/hitl/complete` and the `complete_hitl` MCP tool verify it, when presented, before the pending entry is consumed. |
| x-mcp-header / Mcp-Param-* injection surface (SEP-2243) | Structurally immune: southbound headers to the upstream MCP are built from a fixed allowlist, never from tool-call arguments or any inbound header, and tool schemas are locally authored rather than lifted from the upstream's own `tools/list`. Pinned by a dedicated adversarial-input test suite. |

## Waiting on SDK support (@modelcontextprotocol/sdk still speaks 2025-11-25)

| Spec item | Planned mapping |
|---|---|
| MRTR input_required results (SEP-2322) | The pending envelope this release ships becomes an in-protocol `input_required` result carrying the same `requestState`; a push step-up maps to a bare `requestState` round-trip, transient-email OTP becomes a form-mode `ElicitRequest`. `complete_hitl` becomes that result's retry leg. |
| Stateless core / per-request `_meta` (SEP-2575, SEP-2567) | An SDK transport upgrade; the gateway's `/mcp` handler is already stateless per request (`sessionIdGenerator: undefined`, a fresh `McpServer` + transport built per call). |
| resultType / ttlMs / cacheScope on results (SEP-2549) | Emitted by the SDK's own result types once the SDK is bumped; `server/discover`'s pre-handler already emits this shape today because it is answered by hand ahead of the transport, and the tool surface itself is config-static (built once from `tools.json`) and cache-friendly already. |
| -32022 version negotiation | Owned by the SDK's transport layer once it implements the 2026-07-28 handshake; the `Mcp-Method`/`Mcp-Name` validation and `server/discover` pre-handler above intentionally leave that negotiation alone. |

## Retired codes

The gateway emits no `-32002` anywhere in its own source. Every `/mcp` tool
is registered from the same `tools.json` that gates `/tool`, so a `tools/call`
naming an unregistered tool never reaches gateway code at all - the SDK
itself rejects it, and already does so as `-32602` (`InvalidParams`, "Tool
`<name>` not found"), not `-32002`. A tool name the gateway's own tier
policy denies (a `/tool`-only "unknown tool" that was never configured, or a
configured tier-4 tool) never produces a JSON-RPC error either way - both
come back through the normal envelope (`{ ok: false, denied: true, reason:
"unknown_tool" }` / `"policy_deny"`), per the [API reference](api.md).

## Explicitly out of scope

This release does not bump the SDK beyond its existing `^1.29.0` range,
implement MRTR result types, emit `resultType`/`ttlMs`/`cacheScope` on
SDK-constructed results, implement `-32022`/`-32000` negotiation behavior,
require (rather than validate) `Mcp-Method`/`Mcp-Name`, or advertise
`2026-07-28` as a supported protocol version anywhere. It also does not
forward `Mcp-Param-*` headers southbound or honor an `x-mcp-header` value
sourced from upstream tool schemas - both are deliberate refusals, covered
in the [threat model](../threat-model.md).
